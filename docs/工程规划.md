## 1. 项目概述

- **工程名**：`deepseek-harness-harmony`
- **产品名**：DeepSeek Harness 鸿蒙桌面版
- **一句话定位**：基于「Electron-on-鸿蒙」运行时（`harmonypc-electron`，Electron 37 / Node 22.17.0）的 deepseek-harness 桌面封装——在鸿蒙/OpenHarmony 的 Electron 主进程内跑 dsh Host（含 webserver），渲染进程同源加载 localhost，界面 100% 复用 dsh Web UI，功能与 `deepseek-harness-desktop` 基本一致。

- **与 desktop 的关系**：架构同构（进程内 Host + webserver + localhost 同源数据面），唯一的本质差异是把「Electron 桌面运行时（node_modules/electron）」替换为「Electron-on-鸿蒙运行时（harmonypc-electron 的原生 SO + ArkTS 桥接层）」。

## 2. 背景

### 2.1 deepseek-harness（dsh）

- DeepSeek AI 开源的 agent harness，「一切皆插件」架构，由 [Cordis](https://github.com/cordiverse/cordis) 驱动。
- 原生入口 `dsh web`（浏览器 Web UI）；已完成 **Host/Client 分层**：Host（Node.js）挂 `apiProxy` + `webserver`；Client（浏览器）经 `WebApiClient` 走 HTTP 上行 + WebSocket 下行。
- **关键事实**：dsh 的 webserver **同时服务 SPA dist 与 `/api`**，因此渲染进程加载 `http://127.0.0.1:<port>/` 即为**同源**，fetch `/api` 与 WebSocket 均无需 CORS/鉴权。

### 2.2 deepseek-harness-desktop（架构参考）

- Electron 桌面壳：主进程 `runProfile('desktop')` 挂起 Host，渲染进程 `loadURL(localhost)` 同源加载 dsh Web UI；桌面能力（托盘/通知/无边框/剪贴板）由主进程直连 `ctx` 订阅事件 + 薄 IPC 实现。
- 消费方式：`deepseek-harness` 与 `dsh-market` 为**同级目录源码引用（非 submodule）**，构建期打 4 个 patch（禁用 HMR、禁用 native 目录选择器、symlink→copy、0.0.0.0 放行），构建产物收集进 resources。
- 本工程**直接复用**其架构决策与 patch，仅替换运行时与打包方式。

### 2.3 ohos_electron_hap（运行时旧方案，已弃用 → 见 §18）

> ⚠️ **运行时已切换**：最终落地改用 `harmonypc-electron`（Electron 37 / Node 22.17.0），不再使用 ohos_electron_hap（Electron 34 / Node 20.18.1）。原因与完整方案见 §18。本节保留 ohos_electron_hap 的原理解析——其桥接三件套（aki / adapter / addon + libshim.a）等机制与 harmonypc-electron 同源。

- 一个 HarmonyOS HAP 工程，使 Electron 应用能跑在鸿蒙/OpenHarmony 设备上。
- 模块构成：
  - `electron`：HAP 入口模块（`type: entry`），承载 Electron 原生运行时 SO（`electron/libs/arm64-v8a/`：`libelectron.so`(~160MB)、`libffmpeg.so`、`libc++_shared.so`、`libadapter.so`、`libextractor.so`）。
  - `web_engine`：HAR 桥接模块（`main: Index.ets`），含 ArkUI Web 组件 + 大量 `*AdapterBind.ets`（窗口/通知/剪贴板/权限等）+ jsbindings + cpp；Electron 应用代码放在 `web_engine/src/main/resources/resfile/resources/app/`。
  - `chromium`：独立浏览器 demo 应用（`type: entry`，处理 http/https/pdf URI），**不在**根 build-profile modules 列表、也**不被** electron/web_engine 引用，本工程裁剪不用（见 §16 决策 1）。
- **桥接机制**（Electron ↔ ArkTS）：`aki`(libaki_jsbind.so) + `adapter`(libadaptertest.so) + `addon`(electron-addon.node，链接 `libshim.a`) 三件套。Node 侧 `require('electron-addon.node')` 可调用 ArkTS 方法；ArkTS 侧用 `JsBindingMethod.bind()` 注册方法供 Node 调用。
- 平台特征：`process.platform === 'ohos'`、浮窗 `floatWindow`、`systemPreferences.requestSystemPermission`、`statusBarView` 扩展能力、musl（`-D__MUSL__=1`）、`aarch64`。

## 3. 目标与原则

**目标**：

- 在鸿蒙/OpenHarmony 设备上提供 deepseek-harness 的**一等公民**桌面应用（对标 `deepseek-harness-desktop`），而非「包一层 `dsh web`」的粗壳。
- 100% 复用 dsh Web UI，不 fork UI。

**原则**：

1. **零上游改动**：复用 dsh 现有 HTTP 载体（`WebApiClient` + webserver 路由），不新写 IPC 载体；对 dsh 的改动仅限 4 个 patch。
2. **进程内 Host**：MVP 阶段 Host + webserver 跑在 Electron 主进程（Node.js），直连 `ctx` 订阅事件最省事；渲染进程只认 localhost，将来迁移透明。
3. **只写装配代码**：复用 `runProfile` / 现有插件机制与 harmonypc-electron 已提供的 `*AdapterBind`，桌面能力以主进程启动代码 + 既有桥接注入。

## 4. 核心架构方案（选定）

**核心**：鸿蒙 HAP 内，`electron` 入口模块启动 Electron-on-鸿蒙运行时，其 Node.js 主进程 `runProfile('desktop')` 挂起 dsh Host（webserver 绑定 `127.0.0.1:<空闲端口>`）；渲染进程 `loadURL('http://127.0.0.1:<port>/')` 同源加载 dsh Web UI。

```
┌─ 鸿蒙 HAP ──────────────────────────────────────────────────────┐
│  electron 模块（entry）                                          │
│    ├─ 原生 SO：libelectron.so + libffmpeg.so + libadapter.so …  │
│    └─ EntryAbility → 启动 Electron-on-鸿蒙 运行时                │
│  web_engine 模块（HAR 桥接层）                                   │
│    ├─ ArkUI Web 组件 + *AdapterBind（窗口/通知/剪贴板/权限）      │
│    ├─ jsbindings（JsBindingMethod 注册 ArkTS 方法）              │
│    └─ resfile/resources/app/  ← dsh 产物 + main.js              │
│         ┌─ Electron 主进程（Node.js，承载 dsh Host）────────────┐│
│         │  main.js: runProfile('desktop',['--port','0'])        ││
│         │    ├─ webserver ← 127.0.0.1:<port>，服务 dist + /api  ││
│         │    ├─ apiProxy  ← RPC 网关                            ││
│         │    └─ connection ← /api + WebSocket 注册              ││
│         │  就绪后 loadURL(http://127.0.0.1:<port>/)             ││
│         └────────────────────▲─────────────────────────────────┘│
│                              │ 同源（无 CORS/鉴权）              │
│         ┌────────────────────┴─────────────────────────────────┐│
│         │ 渲染进程：loadURL(localhost) ← 同源                    ││
│         │   标准 dsh Web UI（WebApiClient：fetch /api + WS 事件） ││
│         └──────────────────────────────────────────────────────┘│
└──────────────────────────────────────────────────────────────────┘
```

**与 desktop 的差异对照**：

| 维度 | deepseek-harness-desktop | 本工程（harmony） |
|---|---|---|
| 运行时 | 官方 Electron（npm 依赖） | Electron-on-鸿蒙（harmonypc-electron，构建期 copy） |
| UI 加载 | `loadURL(localhost)` 同源 | 同（Electron 渲染进程 + 嵌入式 Chromium） |
| 后端进程 | 主进程内 Host | 同（Electron-on-鸿蒙的 Node.js 主进程） |
| 数据面 | HTTP + WebSocket（同源） | 同 |
| 桌面能力注入 | Electron `Tray`/`Notification` | 桥接 ArkTS（`*AdapterBind` + addon） |
| 构建 | Electron Forge（Vite + make） | hvigor（DevEco Studio）产 HAP |
| 分发 | 本地打包 exe/deb/rpm | 签名 HAP + `hdc install` |

## 5. 目录结构决策（核心问题回答）

### 5.1 结论

**4 个相关工程全部同级目录并行存放，无需父子关系，无需 git submodule。**

### 5.2 分层分析

相关工程分两类，处理方式不同：

| 工程 | 角色 | 集成方式 | 是否 submodule |
|---|---|---|---|
| `deepseek-harness` | dsh Host（Node 工程） | 同级源码引用 `../deepseek-harness`，构建期收集产物 | 否 |
| `dsh-market` | 插件市场（Node 工程） | 同级源码引用 `../dsh-market`，构建期收集产物 | 否 |
| `harmonypc-electron` | Electron-on-鸿蒙运行时 | 同级源码引用 `../harmonypc-electron`，**构建期 copy 原生 SO + ArkTS 桥接层源码进本工程** | 否 |

**为什么全部用 sibling 而非 submodule**：

1. **desktop 已验证**：dsh / dsh-market 的 sibling 源码引用 + 构建期收集产物模式完全解耦、可独立迭代、CI 二次 checkout 即可，desktop 明确「not a submodule」。
2. **鸿蒙工程对 sibling 只有两种消费形态**——构建期 Node 脚本 copy 产物，或 hvigor HAR 依赖（`file:../xxx`）。二者都不需要 submodule。
3. **submodule 的代价**：版本固定但操作复杂（子模块更新、CI 二次 clone、相对路径耦合），与 desktop 策略不一致，且对「copy 二进制产物」这一形态毫无收益。

**为什么 harmonypc-electron 不能像 dsh 那样仅「源码引用」、而必须「构建期 copy 物理文件」**：

- harmonypc-electron 是**鸿蒙工程**（非 npm 包），其价值是「原生 SO 二进制 + ArkTS 源码 + resfile」。
- hvigor 构建 HAP 时，模块必须**物理存在于本工程的 `build-profile.json5` modules 列表内**，且原生 SO 需在模块 `libs/arm64-v8a/` 固定位置、resfile 需在 `web_engine/src/main/resources/resfile/` 固定位置。
- 跨工程引用「原生 SO + resfile」hvigor 支持很弱（HAR 只覆盖纯 ArkTS 代码，不含 SO 二进制布局与 resfile 资源）。故采用「sibling 存放 + 构建期 copy 进本工程」——**目录同级、产物内嵌**，兼顾对称布局与可构建性。

## 8. 运行时集成方案（collect-runtime）

**目标**：把 `../harmonypc-electron` 的运行时（electron + web_engine 模块 + 原生 SO）构建期 copy 进本工程，实现「sibling 存放、产物内嵌」。

**copy 清单**（`scripts/collect-runtime.mjs`，幂等，可 `--reverse`/增量）：

| 源（../harmonypc-electron/…） | 目标（本工程/…） | 说明 |
|---|---|---|
| `electron/`（整模块，剔除 build/oh_modules/.git） | `electron/` | 入口模块（含 `libs/arm64-v8a/*.so`） |
| `web_engine/`（整模块，剔除 build/oh_modules） | `web_engine/` | 桥接 HAR |
| `chromium/` | 不 copy（裁剪） | 独立浏览器 demo 应用（`type: entry`，处理 http/https/pdf URI），不在根 build-profile modules 列表，也不被 electron/web_engine 引用，dsh 包装无需编译（见 §16 决策 1） |

**关键决策**：

- **SO 二进制不提交进本仓库**（加入 `.gitignore`）：`libelectron.so` ~160MB，从 sibling 构建期 copy 即可，本仓库保持轻量。运行/发布前必须执行 `collect-runtime`。
- **copy 为「同步」而非「一次性」**：上游 harmonypc-electron 更新后重跑脚本即可拉取新 SO/桥接源码。
- **签名配置**：harmonypc-electron 的 `build-profile.json5` 内含调试签名（`signingConfigs` + material 绝对路径），copy 后需替换为本工程自己的签名配置（DevEco 自动签名或华为证书）。

## 9. dsh 集成方案（build-dsh + collect-dsh）

完全对齐 desktop 的集成方式，仅收集目标从 `resources/` 变为 `web_engine/src/main/resources/resfile/resources/app/`。

```bash
node scripts/collect-runtime.mjs   # ① copy ../harmonypc-electron 运行时
node scripts/build-dsh.mjs         # ② git apply 4 patch → pnpm install → build:lib:host + build:lib:client + build:web → build ../dsh-market
node scripts/collect-dsh.mjs       # ③ 收集 dsh 产物 + main.js 进 resfile/resources/app/
```

**dsh 产物收集目标**（`collect-dsh.mjs`）：

```
web_engine/src/main/resources/resfile/resources/app/
├── main.js                     # Electron 入口（编译自 src-main/）：runProfile + loadURL
├── dsh-dist/                   # dsh 构建产物（lib host/client + node_modules + web dist）
│   └── node_modules/dshmarket  # dsh-market 产物（内置插件市场）
└── profiles/desktop/           # 复制到 $DSH_HOME/profiles/desktop
```

**patch 复用**（desktop 已论证，直接搬运；另有 2 个鸿蒙专用 patch）：

| Patch | 目的 |
|---|---|
| `dsh-disable-hmr.patch` | `DSH_DISABLE_HMR` 开关，跳过依赖 `--expose-internals` 的 watch-only HMR |
| `dsh-disable-native-picker.patch` | 目录选择器走 browse（原生 dialog worker 在 Electron 下 spawn 失败） |
| `dsh-symlink-to-copy.patch` | 鸿蒙沙箱禁 symlink（EACCES），`healProfilesModuleFallback` 回退 `cpSync` 递归拷贝 |
| `dsh-allow-all-interfaces.patch` | 移除 webserver `--host 0.0.0.0` 拒绝检查（loopback 隔离需绑全网卡 + 局域网 IP） |

**dsh 消费方式**：与 desktop 一致——`@deepseek-ai/dsh`（apps/cli）只暴露 bin，`runProfile` 从源码 import（`apps/cli/src/profile-boot.ts`），故必须 sibling 源码引用 + 自建前端 dist。

## 10. 桥接机制（Electron ↔ ArkTS）

MVP 的「通知 + 剪贴板」**大部分已由运行时提供**，本工程只做接线：

- **通知**：`web_engine` 已内置 `NotificationAdapterBind.ets`。主进程订阅 `ctx` 的 `session/event`（`approval/requested`、`question/requested`、turn 完成）后，经桥接触发鸿蒙通知。
- **剪贴板图片**：`PasteBoardAdapterBind.ets` 已内置；渲染进程粘贴走 dsh 图片附件路径（`session.prompt` 的 attachment）。
- **权限**：经 `PermissionManagerAdapterBind` / `systemPreferences.requestSystemPermission` 申请（相机、麦克风、目录等按需）。

**桥接三件套（运行时已编译好，无需自建）**：

| 组件 | 产物 | 作用 |
|---|---|---|
| aki | `libaki_jsbind.so` | JS 绑定框架（Node ↔ ArkTS 类型桥） |
| adapter | `libadaptertest.so` | 注册原生方法（`getNativeContext` + `bindFunction`） |
| addon | `electron-addon.node`（链 `libshim.a`） | Node 侧 `require()` 入口，调 `addon.getDir()` 等 |

> 若 MVP 需要新增自定义 ArkTS 能力（如托盘替代方案），按《HarmonyOS Electron 调用 ets 指导文档》扩展 adapter/addon 即可；MVP 阶段预计无需扩展。

## 11. MVP 功能范围与落地映射

**MVP（选定）**：跑起来 dsh Web UI + 剪贴板 + 通知。

| 能力 | 落地方式 | 状态 |
|---|---|---|
| dsh Web UI 在窗口内运行 | 主进程 `runProfile('desktop')` + `loadURL(localhost)` | 核心，必做 |
| 剪贴板图片粘贴 | 渲染进程粘贴 → dsh 附件路径；`PasteBoardAdapterBind` + 权限 | 运行时已支持，接线 |
| 通知 | 订阅 `ctx` 事件 → `NotificationAdapterBind` → 鸿蒙通知 | 运行时已支持，接线 |

**二期（defer）**：

| 能力 | 鸿蒙映射 | 说明 |
|---|---|---|
| 系统托盘 | `statusBarView` 扩展 / `floatWindow` 浮窗 | 鸿蒙 2in1 无传统托盘，语义需重构 |
| 无边框窗口 | `BrowserWindow({ frame:false })` / 透明窗口 | 运行时支持，但非首期目标 |
| 开机自启 / 全局快捷键 | 暂缓 | desktop 亦暂缓 |

**不做（沿用 dsh 标准前端）**：原生文件/目录选择器——使用 dsh Web UI 内置目录浏览（`host.listDirectory` browse 后端）。

## 12. 进程模型与数据流

### 12.1 进程模型

- **Electron 主进程（Node.js）**：承载 dsh Host（webserver + apiProxy + connection），绑定 `127.0.0.1:<空闲端口>`；就绪后 `BrowserWindow.loadURL(localhost)`；订阅 `ctx` 事件触发通知。
- **渲染进程（Chromium）**：`loadURL(localhost)` 同源加载 dsh Web UI。
- **鸿蒙 ArkTS 层**：`electron` EntryAbility + `web_engine` 的 ArkUI 组件承载 BrowserWindow 与系统能力桥接。

### 12.2 数据流

- **上行（unary）**：渲染进程 `WebApiClient.doFetch` → `fetch('/api/<method>')`（同源）→ webserver `/api` 路由 → `toFetchHandler(apiProxy).fetch`。
- **下行（事件帧）**：渲染进程 `WebApiClient.openMux/openHost` → `WebSocket('/api/events.mux' | '/api/events.host')` → 帧流。
- **通知**：主进程直连 `ctx` 的 `session/event`（进程内）→ 桥接 ArkTS 通知。
- **剪贴板**：渲染进程粘贴 → dsh 图片附件路径。

## 13. 构建 / 打包 / 运行流程

## 18. 最终实现记录（Electron 37 落地，真机验证通过）

> 本节记录 2026-08-26 实际落地过程中相对 §1–§17 规划的关键变更与最终方案。核心结论：**dsh Web UI 已在鸿蒙真机（HarmonyOS 6.1.0.135 / API 24）成功运行**，窗口标题 `HOST-OK http://<LAN-IP>:<port>/`，渲染进程成功加载 dsh Web UI（界面含「新建会话」等中文元素）。

### 18.1 运行时选型变更：ohos_electron_hap → harmonypc-electron（Electron 37）

| 项 | 原规划（§2.3） | 最终采用 |
|---|---|---|
| 运行时工程 | `ohos_electron_hap`（Electron 34.0.2） | `harmonypc-electron`（Electron 37.2.3） |
| Node 版本 | 20.18.1 | **22.17.0** |
| 原生 SO | libelectron.so / libffmpeg.so / libc++_shared.so / libadapter.so / libextractor.so | libelectron.so(~172.7MB) / libadapter.so / libffmpeg.so（3 个，在 `electron/libs/arm64-v8a/`） |

**变更原因**：dsh 依赖 Node 22+ 内建能力——`node:zlib.createZstdDecompress`（解压会话产物）与 `node:sqlite`（会话持久化/全文搜索）。Electron 34 的 Node 20.18.1 两者皆无，主进程启动即抛 `TypeError: createZstdDecompress is not a function`；Electron 37 的 Node 22.17.0 内置，问题消除。

### 18.2 关键适配改动（相对 §4 架构方案）

| # | 问题 | 现象 | 解决 |
|---|---|---|---|
| 1 | **loopback 隔离** | 渲染进程访问主进程 `127.0.0.1:<port>` 被鸿蒙 NEXT 进程间网络隔离拦截，Web UI 白屏/加载失败 | webserver 绑 `0.0.0.0`，`loadURL` 改走局域网 IP（`pickReachableHost` 取设备 IP）；profile 覆盖 `web-runtime` 的 `host: '0.0.0.0'` |
| 2 | **symlink 禁止** | 鸿蒙沙箱 `symlinkSync` 抛 `EACCES`，dsh `healProfilesModuleFallback` 初始化失败 | 新增 patch `dsh-symlink-to-copy.patch`：symlink 失败时回退 `cpSync`（递归拷贝） |
| 3 | **HAP 打包超限** | dsh-dist 5 万+ 小文件，hvigor 打包阶段卡死/内存爆 | dsh-dist 先 `tar -czf --format=ustar` 压成单个 `dsh-dist.tar.gz`(~143MB)，运行时 `createGunzip` 流式解压 + 剥离 `dsh-dist/` 前缀 |
| 4 | **原生模块 ABI** | dsh-dist 在 Windows 上收集，`sharp`/`node-pty`/`koffi` 二进制是 win32-x64，鸿蒙 aarch64 无法加载 | `sharp` 用纯 JS stub（见 §18.3）；`node-pty`(subprocess)、`koffi`(sandbox) 对应插件及依赖在 `cordis.patch.yml` 禁用 |
| 5 | **corepack pnpm** | desktop 用 `corepack pnpm`，鸿蒙构建环境 corepack 不可用 | `build-dsh.mjs` 改为直接 `pnpm` |

### 18.3 MVP 取舍（原生模块桩化/禁用）

| 能力 | 依赖 | 状态 | 影响 |
|---|---|---|---|
| 图片附件真实校验/缩略图 | `sharp`（libvips） | ⚠️ 纯 JS stub（metadata/raw 返回固定值，no-op） | 附件仍可上传/关联，但不做真实解码与缩略图生成 |
| 终端（bash 工具） | `node-pty` | ❌ 禁用（`subprocess`+`sandbox`+`bash-sandbox` 插件） | 无法运行 shell 命令类工具 |
| 进程沙箱 | `koffi`（landlock） | ❌ 禁用（`permission` 插件） | 工具调用无沙箱隔离 |
| 会话持久化 / 全文搜索 | `node:sqlite` | ✅ 正常（Node 22 内建） | 无需 native 编译 |

**cordis.patch.yml 最终禁用集**：`subprocess`、`sandbox`、`bash-sandbox`、`permission`（4 个）；`attachment-local` 保留启用（配合 sharp stub 提供 `attachments` 服务，供 `host-apiproxy` 依赖）。

**sharp stub 位置**：`dsh-dist/node_modules/sharp/dist/index.mjs` + `index.cjs`（`function sharp(input, options)` 返回可链式对象，`metadata()` 返回 `{format:'png',width:1,height:1}`、`raw().toBuffer()` 返回空 Buffer）。

**关键实现点**：

| 步骤 | 说明 |
|---|---|
| 4 个 patch | `dsh-symlink-to-copy`（symlink EACCES→cpSync 回退）、`dsh-allow-all-interfaces`（移除 `0.0.0.0` 拒绝检查）、`dsh-disable-hmr`、`dsh-disable-native-picker`；`build-dsh.mjs` 幂等应用（`--reverse --check` 跳过已应用） |

### 18.5 交叉编译优化路径（恢复完整能力）

原生模块（node-pty / koffi / sharp）需按 HarmonyOS aarch64 工具链重新编译，参考《Electron37 的 node 头文件（Headers）使用指导》：

```bash
# 工具链：DevEco SDK 自带 OpenHarmony LLVM
clang --target=aarch64-linux-ohos -D__MUSL__=1 \
  --sysroot=<OHOS_SDK>/native/sysroot \
  -I<node 头文件目录> -I<electron 头文件目录> \
  -fPIC -shared module.cc -o module.node \
  <链接 libshim.a 以解析 electron 运行时符号>
```

| 模块 | 工程量 | 说明 |
|---|---|---|
| `node-pty` | 小 | 恢复终端（bash 工具）；需 forkpty/posix 语义在 musl 下适配 |
| `koffi` | 小 | 恢复沙箱（landlock syscall 封装） |
| `sharp`（libvips） | 大 | libvips + 全部图像编解码器交叉编译，工作量大，可最后处理 |

**产物落地**：编译出的 `.node` 放入 `electron/libs/arm64-v8a/`（或 resfile 内 app 可加载路径），并移除 `profiles/desktop/cordis.patch.yml` 中对应插件的 `disabled: true` 即可。
