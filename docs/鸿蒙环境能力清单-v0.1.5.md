## 三、用户目录（你授权的桌面/文档/下载）

| 目录 | 路径 | 状态 |
|---|---|---|
| 桌面 | `/storage/Users/currentUser/Desktop` | ⚠️ 新建失败 |
| 文档 | `/storage/Users/currentUser/Documents` | ⚠️ 新建失败 |
| 下载 | `/storage/Users/currentUser/Download` | ⚠️ 新建失败（单数，无 `Downloads`） |

**两层权限是分开的，这点最容易误解：**

1. **DSH 策略层**：你的授权**没有写进策略**，三个目录默认仍被拒（`file access denied under workspace-write`），每次访问都要单独提权审批。
2. **鸿蒙系统层**：授权**是生效的**——临时目录和临时文件确实在 Desktop 里建成功了。
3. **真正的拦路虎是 DSH 自己**：新建文件走 `link()` 硬链接发布，而 hmdfs 不支持硬链接 → 稳定复现 `EPERM ... link`。同一段代码里**覆盖已有文件走 `rename()`**，hmdfs 支持，所以理论上可行。

> 相关证据：`dsh-dist/node_modules/@deepseek-ai/dsh-fs-local/lib/index.js` 第 532-543 行；hmdfs 特性见 [鸿蒙 PC 底层开发技术详解（六）](https://harmonypc.csdn.net/69f8a31c0a2f6a37c5a7d4bd.html)。

**v0.1.6 补充：实际是三层，不是两层**（详见 §13.5）

| 层 | 内容 | 证据 |
|---|---|---|
| ① DSH 沙箱白名单 | 白名单 = **session workspace 一个根** + `/tmp` + `os.tmpdir()` | `packages/sandbox/sandbox/src/roots.ts:52-55`；`sandbox-policy/src/index.ts:163-170` |
| ② DSH 建文件走硬链接 | `writeFileAtomic` 新建分支走 `link()`，失败无回退 | `packages/fs/fs-local/src/fsio.ts`：`link` 在 616-621 行；`throwGuardedCreateFailure` 519-554 行 |
| ③ 鸿蒙授权等级 | Download/Documents = `normal`（一次弹窗即可）；**Desktop = `system_basic`（需 ACL，不可上架）** | 官方 `permissions-for-all-user.md` / `restricted-permissions.md` |

②的源码证据链（已交叉验证）：hmdfs 内核里 `hmdfs_dir_inode_ops_local` **没有 `.link` 处理器**，因此 `link()` 只能返回 `EPERM`——这与实测现象完全一致。`sensitive` 是 opt-in 挂载项，**hmdfs 默认大小写不敏感**。

# 第二部分：受限能力根因分析与恢复方案（v0.1.6 增补）

## 十一、根因分层模型（关键结论）

**当前受限项不是同一类问题。** 把它们统一当成「鸿蒙环境限制」会导致方案选错。实际分四层：

| 层 | 性质 | 可恢复性 | 涉及项 |
|---|---|---|---|
| **L1 平台硬约束** | 鸿蒙产品策略 / 权限体系 | 难；部分**不可上架** | fork+exec、pty、任意二进制执行、Desktop 目录权限 |
| **L2 原生产物缺失** | dsh-dist 在 Windows 收集 → `node-pty`/`koffi` 是 win32-x64，aarch64 无法加载 | 交叉编译可恢复，但受 L1 封顶 | 终端、进程沙箱、ripgrep 搜索 |
| **L3 本工程配置选择** | `cordis.patch.yml` + agent preset 的 disabled 行 | **改配置即可，成本最低** | skill、todo、goal、jobs、workflow、subagent、web、present、str_replace_editor |
| **L4 dsh 上游接口缺失** | `ctx.fs` seam 只有 13 个原语，**根本没有** delete/rename/copy/mkdir | 与鸿蒙无关，需自研或上游改 | 删除、移动、重命名 |

**一句话**：真正被鸿蒙卡住的只有「跑任意二进制 / pty」；被原生产物卡住的是终端与搜索；**其余绝大部分是本工程的配置取舍或 dsh 本身的设计边界**。

**桌面版对照（决定性证据）**：`deepseek-harness-desktop/profiles/desktop/cordis.patch.yml` **只**覆盖 `web-runtime` 与 `dsh-market`，**没有**禁用 `subprocess`/`sandbox`/`permission`，也**没有**禁用 preset 里的 `tool-bash`/`tool-fs-search`。所以桌面版有终端、有内容搜索——**鸿蒙版多出来的限制，是本工程自己在 L3 加的**（动因是 L2）。

## 十二、受限能力 × 根因 × 恢复方案（主表）

| # | 受限能力 | 根因 | 恢复方案 | 成本 |
|---|---|---|---|---|
| 1 | 终端 / shell 命令 | L2+L1+L3（四重） | T1 非 pty 的 exec 工具（推荐）／T3 HNP+系统终端／T4 executableBinaryPaths | 中／小 |
| 2 | 进程沙箱 | L2（koffi）+ L1（landlock 在 OHOS 内核未必有） | 不恢复（推荐），或 koffi + fs 围栏替代 | 小 |
| 3 | 目录列举 / 内容搜索 | L2（ripgrep）+ L3（preset 禁用） | **C2 挂 `str_replace_editor`（纯 JS，改 YAML）**；C1 纯 JS 重写 glob/grep | 极小／小 |
| 4 | 删除 / 移动 / 重命名 | **L4（与鸿蒙无关）** | **D1 自研纯 JS fs 工具插件**；D2 上游加 seam 原语 | 小 |
| 5 | 用户目录建文件失败 | L1/L3：`link()` 硬链接 + hmdfs 无 `.link` | **E1 扩展现有 hardlink→rename patch 到 `fsio.ts`** | 小 |
| 6 | 用户目录每次审批 | L3：`writableRoots()` 只含 workspace | **E2 可配置额外可写根** | 小 |
| 7 | 图片校验/缩略图 | L2（libvips） | F1 纯 JS 图片头解析（真实尺寸 + 校验） | 小 |
| 8 | `job_*` 空壳 | L3 派生：无 shell 可启动任务 | G1 随 #1 一起恢复；G2 subagent 充当后台任务 | — |
| 9 | `skill` 点不动 | **L3 纯配置** | H1 preset 里重新挂载 + 放技能目录 | 极小 |
| 10 | 提权静默放行（安全） | L3：`approval` 行未接线到用户确认 | J1 approval → 鸿蒙通知 + fail-closed | 小 |
| 11 | 后台常驻 | 未声明 `backgroundModes` | K1 长时任务（TASK_KEEPING，2in1/API21+） | 小 |
| 12 | 托盘/无边框/自启/自动更新 | Phase 2 未做 | K2 statusBarView / 浮窗 / 应用内更新 | 中 |

## 十三、逐项分析

### 13.1 终端与命令执行（最复杂的一项）

**四重根因**（缺一不可，所以别只修一处）：见 §四的表格。

**关键洞察**：`dsh-tool-bash` 的依赖链是 `ctx.shell` → `bash-local`/`bash-sandbox` → `ctx.subprocess` → **node-pty**。即「命令执行」与「PTY」被 dsh 绑在一起，真正过不去的是 PTY。

**平台侧官方结论（本项的天花板）**

| 结论 | 出处 |
|---|---|
| 手机设备：「当前禁止三方应用在手机设备上 Fork 进程」 | `harmonyos-faqs/faqs-ability-29` |
| PC/2in1 是否允许 `fork`+`execve`：**无官方文档背书**（社区答主称「pc 上不限制」，非官方） | `harmonyos-faqs/faqs-ability-112`（正文 JS 渲染未取到） |
| `fork`/`clone`/`execve`/`posix_spawn` **不在** seccomp 拦截清单 | `guidance-on-ndk-libc-interfaces-affected-by-permissions.md` |
| `forkpty`/`openpty`/`posix_openpt`/`popen` **在** SELinux 受影响清单（失败表现为 `EACCES`） | 同上 |
| Native Child Process：`OH_Ability_CreateNativeChildProcess` 等，**只能 dlopen 自有 .so + 调命名入口**，不支持 UI，`MainProc` 返回即退出，单进程 ≤50（API15+）/ 总数 ≤512；API13 仅 2in1，API14+ 加 Tablet | `capi-nativechildprocess-development-guideline` |

**运行期二进制证据（harmonypc-electron）**

| 符号 | libelectron.so | libadapter.so |
|---|---|---|
| `uv_spawn` | **已定义** | 无 |
| `fork` / `execve` / `pipe` / `flock` / `symlink` / `link` | **UNDEF**（从 OHOS libc 动态导入） | 部分 |
| `posix_spawn` / `forkpty` / `openpty` / `landlock` | **完全不存在** | 无 |
| 进程创建后端 | — | `ChildProcessManager::StartArkChildProcess` + `AppSpawnCommunication`（↔ `ProcessAdapter.ets` 的 `childProcessManager.startArkChildProcess`） |

→ **只能起 Ark 子进程，不能 exec 任意 ELF。**

**方案（按推荐度）**

- **T1（推荐）解耦「执行」与「PTY」**：给 dsh 打 patch，让 `subprocess` 服务在 `openharmony` 平台走 `child_process.spawn` 的**非 pty** 后端（管道即可），而非 node-pty；或自研一个最小 `tool-exec` 插件直接调 `node:child_process`（宿主在 Electron 主进程，node 能力可用）。**一次性恢复 #1 命令执行、#3 内容搜索的 subprocess 依赖、#8 jobs。** 唯一不确定项：PC/2in1 上 `fork`+`execve` 是否被放行 → 先做探针验证（见 §十六）。
- **T3（发布可用）HNP + 系统终端**：官方支持把可执行文件打成 HNP 包（`module.json5` 的 `hnpPackages`，**仅 entry 模块**；public 包落 `/data/service/hnp`）。鸿蒙 PC **自带终端**（HiShell，官方消费者文档列出 `sh`/`sudo`）。把 CLI 工具作为 public HNP 发布，**用户在系统终端里调用**。缺点：应用无法编程驱动它。
- **T4（官方路径但不可上架）**：`executableBinaryPaths`（**API 24 起，仅 PC/2in1**）+ `extractNativeLibs`/`collectAllLibs` + `.permission` 节 + `binary-sign-tool` 签名，配套 `ohos.permission.ALLOW_EXTERNAL_NATIVE_CODE`（system_basic / PC/2in1 / API 23）。ACL 官方明确「**不可用于发布上架应用市场**」→ 仅自用/调试分发。
- **T2（不推荐）交叉编译 node-pty**：工具链见 `工程规划.md §18.5`（`clang --target=aarch64-linux-ohos -D__MUSL__=1 ... libshim.a`），社区有 `555cui/ohos-node-pty`。**但即使编译成功，`forkpty`/`openpty` 会被 SELinux 拒（EACCES）**。性价比最低。

> 建议：**放弃 pty，走 T1**；T3/T4 作为可选增强。

### 13.2 进程沙箱（koffi / landlock）

**根因**：koffi 是 win32-x64；且 `landlock` 是 Linux LSM，OHOS 内核是否具备**未证实**（`libelectron.so` 里连 `landlock` 字符串都没有）。

**方案**
- **B1（推荐）不恢复**。`sandbox` 插件只在**有 shell 时**才有意义（它隔离的是工具执行进程）。当前无 shell，而**文件面已有 `fs-sandbox`（纯 JS）在起作用**（`packages/fs/fs-sandbox/src/index.ts:122-144` 的 `checkedTarget`），叠加 `approval`。所以「工具调用无沙箱隔离」这个描述只在恢复终端后才成立。
- B2 若恢复 shell：交叉编译 koffi（工程量小），但需先确认 OHOS 内核支持 landlock；否则退化为「路径围栏 + 审批」。
- B3 **不要**用 `ohos.permission.CUSTOM_SANDBOX`（system_basic / API 18）替代 —— 它改的是**应用自身沙箱类型**（动态沙箱），不是进程沙箱。

### 13.3 目录列举 / 内容搜索（`glob`/`grep`）

**根因**：`dsh-tool-fs-search` 的 `inject` 是 `['tools','systemPrompt','subprocess']` —— 靠 `@vscode/ripgrep` **外部二进制**；再叠加 preset 层禁用（`main.js:174-178`）。

**方案**
- **C2（强烈推荐，改 YAML 即可）**：挂载 `@deepseek-ai/dsh-tool-str-replace-editor`。它是 **PURE**（`inject: ['tools','fs']`，`src/index.ts:428-435`），提供 `view`/`create`/`str_replace`/`insert`，其中 **`view` 对目录路径会返回目录清单**。零原生依赖；它不在任何 bundle 的禁用列表里（只是没有任何 bundle 挂它）——在 standard preset 加一行即可。
- **C1（推荐，纯 JS）**：新写 glob/grep 工具，直接基于 `ctx.fs.listDir` + `readText` 实现（seam 已具备）。**这是替代 ripgrep 的正解**：内容搜索本质是遍历 + 正则，JS 够用，且完全绕开 subprocess。
- C3 交叉编译 `@vscode/ripgrep` 的 aarch64 产物 + T1 的非 pty 执行后端 —— 成本高于 C1，收益相近。

> ⚠️ 细节：`glob` **只返回文件、从不返回目录**（`glob.ts:314-317`）。所以「列目录」不能指望 glob，要靠 `listDir` 工具或 `str_replace_editor` 的 `view`。

### 13.4 删除 / 移动 / 重命名（**原清单此处归因需修正**）

**现象成立，但归因错误：这不是鸿蒙限制，桌面版一样。**

证据：`packages/fs/fs/src/index.ts` 的 `abstract class FileSystem`（第 86 行起）**完整方法清单只有 13 个**：

`resolve` / `processPath` / `processPathFromHostPath` / `fileUrl` / `contains` / `stat` / `lstat` / `readText` / `streamText` / `readBytes` / `readByteRange` / `listDir` / `writeText` / `editText`

**没有 delete/remove/unlink、没有 rename/move、没有 copy/mkdir/watch。** 包 README 的 Known Limitations 也自述：「Thirteen primitives only — no delete, rename, copy, or watch」。`tool-fs` 只暴露 `read`/`read_image`/`write`/`edit`；`tool-str-replace-editor` 只有 `view`/`create`/`str_replace`/`insert`。删除/移动在 dsh 里**唯一**的途径是 shell 的 `rm`/`mv`。

**方案**
- **D1（推荐）自研纯 JS fs 工具插件**：宿主跑在 Electron 主进程，`node:fs` 的 `rm`/`rename` 直接可用，而 `fs-local` 内部本来就 import 了 `rename`/`rm`。写一个插件注册 `delete`/`move` 工具（在 `ctx.fs` 的围栏语义下工作），在 preset 挂载。→ agent 终于能清理自己产生的临时文件（解决 §十的遗留物）。
- D2 上游贡献：给 `FileSystem` seam 补 `remove`/`rename`（更规范，但要过上游评审）。
- D3 若 T1 落地，`rm`/`mv` 也能覆盖，但**不应把 shell 作为唯一途径**。

> 鸿蒙侧附加约束（若目标是用户目录）：官方 hmdfs 文档写「**rename：仅支持同目录操作**」；内核源码里 `hmdfs_rename_local` 的守卫是 `-EACCES`（非普通文件名）/`-EPERM`（跨 view）/`-EXDEV`（跨 device）/`-EINVAL`（flags≠0），但**没有显式同目录检查** —— 文档与源码有张力，**按文档的保守契约实现**（跨目录用 copy+delete）。

### 13.5 用户目录写入失败 + 每次审批（两个独立问题）

三层根因见 §三的表格。核心是第 ② 层：`writeFileAtomic` 的**新建分支走 `link()`**（`fsio.ts:616-621`），而 hmdfs **没有 `.link`**，`throwGuardedCreateFailure`（519-554）**只识别 `EEXIST`/目标已存在，对 `EPERM`/`EACCES`/`ENOTSUP`/`EXDEV` 无回退** → 一路抛 `FS_IO_ERROR`。这完美解释「新建失败、覆盖可行」（覆盖走 631-632 行的 `rename()`）。

**方案**
- **E1（必做，十几行）**：把现有 `patches/dsh-v0.1.5-rc.2/dsh-hardlink-to-rename.patch` **扩展到 `packages/fs/fs-local/src/fsio.ts`** —— 当 `linkFile` 因 `EPERM`/`EACCES`/`ENOTSUP`/`EXDEV` 失败**且目标不存在**时，回退 `rename(tempPath, absolutePath)`。
  ✅ 可行性已验证：staging 目录建在 `dirname(absolutePath)` 下的 `.name.<pid>.<uuid>.tmpdir`（**同目录**！），满足 hmdfs「rename 仅同目录」约束；uuid 也规避了 hmdfs 大小写不敏感带来的临时名碰撞。
- **E2（推荐）**：给 `writableRoots()`（`packages/sandbox/sandbox/src/roots.ts:52-55`）加「额外可写根」来源（环境变量如 `DSH_EXTRA_WRITABLE_ROOTS`，或扩展 `SandboxExecutionPolicy`）→ 免去逐次审批。注意 bash 的 bwrap/landlock profile 是**另一处**（`sandbox-local/src/profiles.ts:16-36`）。
- **E3 发布策略**：优先 Documents/Download（`normal`，一次弹窗即可）；Desktop 走 ACL（`system_basic`，仅自用/调试版）；上架版用 **FilePicker + `FILE_ACCESS_PERSIST`**（normal，API 12 起）—— 但注意**每次启动必须 `activatePermission` 手动激活**、**卸载会清空**（API 24 新增 `ohos.fileshare.supportPreservePersistentPermission` 保留能力）。
- **E4（不推荐但要知道）**：`DSH_PERMISSION_MODE=danger-full-access` → `approval` 变 `never`、`fs-sandbox` 不设围栏。会让「每次审批」消失，但把围栏整个拆掉。鉴于 §13.10 的发现（提权本来就能静默拿到），当前围栏**接近于仪式** —— 真正该做的是 E1+E2+J1。

### 13.6 图片附件校验 / 缩略图（sharp）

**根因**：libvips 在 aarch64-ohos 不可用 → `collect-dsh.mjs` 写入纯 JS stub（`metadata()` 固定返回 `{format:'png',width:1,height:1}`）。

**方案**
- **F1（推荐，成本极低）**：纯 JS 解析图片头（PNG/JPEG/GIF/WebP 的 magic + 尺寸字段），替换 stub 的固定值 → 恢复**真实校验 + 正确尺寸**。缩略图可不生成（Web UI 侧浏览器能解码显示）。
- F2 交叉编译 libvips：工程量「大」（`工程规划.md §18.5` 自评），不推荐。
- F3 用 OHOS 图像框架（ArkTS `image` 模块）做解码/缩略图：更贴合平台，需新增 Adapter/桥接，中等成本。
- 补充：`read_image` **存在且是 PURE**（`tool-fs/src/read-image.ts:210`），「模型读图」大概率本来就可用 → 列入回归清单。
  > 🔧 **勘误（见 §19.3）**：实测**否证**「大概率可用」。读取一个合法的 1×1 PNG 即失败：`Error: The undefined PNG could not be converted to the normalized 8-bit sRGB form.` 根因是 sharp 纯 JS stub 只让 `metadata()` 返回固定值，**不具备附件归一化所需的 sRGB / 8-bit 转换能力**。失败点在**读图的归一化步骤**，不是缩略图 → 影响面大于本节预估：**`read_image` 与图片附件链路整体不可用**，F1（纯 JS 头解析）不足以修复。

### 13.7 `job_list`/`job_output`/`job_kill` 空壳

**根因**：三个工具来自 `dsh-tool-jobs`（**PURE**，`inject: ['tools','jobs','systemPrompt']`，只管注册表）。缺的是**能启动后台任务的执行后端** —— 能启动的 `tool-bash-persistent`/`persistent-shell` 被禁（L3 + 派生于 L2）。原清单「能查询但没有任何工具能启动任务」的判断**准确**。

**方案**：G1 随 #1（T1 非 pty exec）一起恢复；G2 或直接把 subagent 当后台任务用（`tool-subagent` 已配置 `backgroundMode: continuable`，且已在 preset 中启用）。

### 13.8 `skill` 点不动

**根因**：**纯配置问题（L3）**。`dsh-web-app/cordis.patch.yml` 显式禁用了 `skill-filesystem`（行 402）与 `tool-skill`（行 405）；且没有技能目录。两者都是 **PURE**（`skill-filesystem` inject `['skills']`，无 subprocess）。

**方案 H1（极小成本）**：在 profile 覆盖层或 preset 里重新挂载 `skill-filesystem` + `tool-skill`，并把技能目录放到运行时根（`includeShippedRoot` / `includeUserRoot` 机制：默认根 = 包内 `presets/` + `$DSH_HOME/.agent-presets`）。→ 立即可恢复。

### 13.9 其余 ❓ 未实测项（「没测」而非「受限」）

`read_image`、`todo_write`、`goal`、`present`、`ask_user_question`、`subagent_fork`、`send_message`、`interrupt_agent`、`workflow`、`ralph`、子代理 —— 这些在 `standard` preset 里**都是启用的**，且都是 **PURE**。它们在 `dsh-web-app` 的禁用列表里被禁，但 standard preset 会**重新挂载**（这是 dsh 的 host-plane / agent-plane 两层设计）。

`src-main/main.js` 的运行时补丁**只禁了 3 行**：`tool-bash`、`tool-fs-search`、`persistent-shell`（`HARMONY_DISABLED_PRESET_ROWS`），其余 preset 行原样保留。

**方案 I1**：安排一次真机「能力回归清单」，逐项实测；对确认缺失项再查 preset 行。零成本、高信息量。

> ⚠️ 顺带发现一处**构建期死代码**：`collect-dsh.mjs` 的 `patchAgentPresets()` 目标是 `<distDir>/config/agent-presets`，但实测 `dsh-dist/` 下**不存在**该目录，所以该步是 no-op；真正生效的是 `main.js` 的 `patchAgentPresetsRuntime()`（在 `node_modules/@deepseek-ai/dsh-agent-presets/presets` 里改）。补充：`config/agent-presets` **确实是** dsh 0.1.5 的安装期挂载路径（`apps/cli/package.json` 的 `dsh.configTrees: [{mount:"config/agent-presets", ...}]`），但它**不是运行期默认根**。建议把构建期与运行期补丁统一到一处。

### 13.10 安全发现：提权通道静默放行（**已于 §19.1 否证，本节结论作废**）

> 🔧 **勘误（见 §19.1）**：本节「审批的呈现/拒绝链路没有接到用户」的**根因判断错误**。真机复测证明审批链路完整可用：UI 会渲染 `等待审批` 面板（含理由、`拒绝` / `允许一次`），agent 阻塞等待，拒绝后返回 `the user rejected escalating this operation to "danger-full-access"`。源码侧亦印证 fail-closed：`ApprovalService.decide()` 的 waterfall 终结默认值是 `() => Promise.resolve('unavailable')`（`packages/interaction/user-approval/src/index.ts:274`），调用方对 `unavailable` 一律拒绝（`packages/core/tools/src/index.ts:1713-1715`、`packages/sandbox/sandbox/src/escalation.ts:186`）。**故 J1 无可开发项**。下方 J1/J2/J3 方案仅作历史记录保留。

**现象**（§八第 1 条）：提到 `danger-full-access` 后，工作区外文件真的建成，**全程没有任何一次拒绝**。

**机制**：`profiles/desktop/cordis.patch.yml` 禁用了 `permission`（`dsh-permission-presets`），但**没有**禁用 `approval`（`dsh-user-approval`）。`dsh-base/cordis.patch.yml:224-227` 给 `approval` 的 policy 是 `DSH_PERMISSION_MODE === 'danger-full-access' ? 'never' : 'ask'`，默认 `ask`。所以审批**应该**发生 —— 但没有拒绝，说明**审批的呈现/拒绝链路没有接到用户**。

**方案**
- **J1（推荐）**：把 `approval` 请求接到**鸿蒙通知 + 显式确认**（`NotificationAdapter` 运行时已具备 `@ohos.notificationManager`），并在主进程侧实现「无应答 = 拒绝」的 fail-closed 语义。
- J2：`danger-full-access` 设为需二次确认。
- J3：若产品上确实不需要提权，干脆把 policy 固定 `never` 并让 fs 工具返回明确错误 —— 现在的状态是「假审批」，比明确关闭更危险。

**结论（三条，均与文档原判断相反或需修正）**

1. **围栏是生效的、且是 fail-closed 的**。工作区外写入被 `FS_SANDBOX_DENIED` 拒绝，**且拒绝发生在审批之前**（提示文案自称 "the approval prompt asks the user"，即拒绝≠审批被跳过）。`profiles/desktop/cordis.patch.yml:31` 明确写了 `sandbox-policy/pwsh-sandbox/fs-sandbox 不额外禁用`，与实测一致。
2. **审批链路本来就是通的**：有理由说明、有「拒绝 / 允许一次」两个动作、有阻塞等待、拒绝后返回明确错误。源码侧印证：`ApprovalService.decide()` 的 waterfall 终结默认值是 `() => Promise.resolve('unavailable')`（`packages/interaction/user-approval/src/index.ts:274`），而所有调用方对 `unavailable` 一律**拒绝**（`packages/core/tools/src/index.ts:1713-1715`、`packages/sandbox/sandbox/src/escalation.ts:186`）；Web UI 侧 `packages/client/ui-approval` 的 `ApprovalPanel.tsx` 负责呈现，注册于 `packages/bundle/web-app/cordis.patch.yml:252-253`。
3. **因此 §八 第 1 条与 §13.10 的「提权静默放行」归因不成立**。当时那次工作区外写入之所以成功，是**有人在审批面板上点了「允许一次」**，而不是审批未接线。→ **J1 无需开发**（原方案「把 approval 接到鸿蒙通知 + fail-closed」是在修一个不存在的缺陷；且现有实现已具备 fail-closed 语义，贸然改接通知反而有降低安全性的风险）。

### 19.3 新发现缺陷：`read_image` 实际不可用（**修正 §13.6**）

§13.6 与 §七原判断为「`read_image` 大概率本来就可用」。实测**否证**：读取工作区内一个合法 1×1 PNG（70 字节，magic `89504e470d0a1a0a` 校验通过）即失败：

```
Error: The undefined PNG could not be converted to the normalized 8-bit sRGB form.
```

根因：`collect-dsh.mjs` 写入的 sharp 纯 JS stub 只让 `metadata()` 返回固定值，**不支持附件归一化所需的 sRGB / 8-bit 转换**，因此失败点不在「缩略图」，而在**读图的归一化步骤**。

→ 影响面比 §13.6 预估的大：不是「校验变 no-op、尺寸不准」，而是 **`read_image` 与图片附件链路整体不可用**。`F1`（纯 JS 图片头解析）不足以修复，需要让 stub 真正实现归一化所需的转换（或走 F3 的 OHOS 图像框架）。**已记为已知缺陷，暂缓处理。**
