## C. 关键结论与依据

### C.1 根因分层模型（L1-L4）

当前受限项不是同一类问题。把它们统一当成「鸿蒙环境限制」会导致方案选错。实际分四层：

| 层 | 性质 | 可恢复性 | 涉及项 |
|---|---|---|---|
| **L1 平台硬约束** | 鸿蒙产品策略 / 权限体系 | 难；部分**不可上架** | pty、Desktop 目录权限 |
| **L2 原生产物缺失** | dsh-dist 在 Windows 收集，`node-pty`/`koffi` 是 win32-x64，aarch64 无法加载 | 交叉编译可恢复，但受 L1 封顶 | 终端、进程沙箱、ripgrep 搜索、图片处理 |
| **L3 本工程配置选择** | `cordis.patch.yml` + agent preset 的 disabled 行 | **改配置即可，成本最低** | skill、todo、goal、jobs、workflow、subagent、web、present、str_replace_editor、exec |
| **L4 dsh 上游接口缺失** | `ctx.fs` seam 原语里没有 delete / rename / copy / mkdir / watch | 与鸿蒙无关，需自研或上游改 | 删除、移动、重命名、复制、改权限 |

**一句话**：平台侧真正卡住的只有 PTY（`forkpty`/`openpty` 被 SELinux 拒）；`fork`+`execve` 已实测放行，不是平台限制。被原生产物卡住的是终端与搜索；其余绝大部分是本工程的配置取舍或 dsh 本身的设计边界。

### C.2 桌面版对照（决定性证据）

`dsh-desktop/profiles/desktop/cordis.patch.yml` **只**覆盖 `web-runtime` 与 `dsh-market`，**没有**禁用 `subprocess`/`sandbox`/`permission`，也**没有**禁用 preset 里的 `tool-bash`/`tool-fs-search`。桌面版因此有终端、有内容搜索。**鸿蒙版多出来的限制，是本工程自己在 L3 加的**（动因是 L2）。

### C.3 逐项根因结论

**终端 / shell（四重根因，缺一不可）**

| 层 | 内容 | 出处 |
|---|---|---|
| 产物层 | `node-pty` 在 dsh-dist 里是 **win32-x64**（Windows 上收集），aarch64 无法加载 | `dsh-dist` 内 `node-pty` 二进制平台 |

依赖链是 `ctx.shell` → `bash-local`/`bash-sandbox` → `ctx.subprocess` → `node-pty`，即「命令执行」与 PTY 被 dsh 绑在一起。`fork`+`execve` 本身放行（C.5），过不去的只是「用 node-pty 实现」，而执行不必经过 PTY（T1 即为此设计）。

**进程沙箱（koffi / landlock）**

- 根因：koffi 是 win32-x64；`landlock` 是 Linux LSM，OHOS 内核是否具备**未证实**（`libelectron.so` 里连 `landlock` 字符串都没有）。
- 结论：**不恢复**。`sandbox` 插件只在有 shell 时才有意义（它隔离的是工具执行进程）。当前无 shell，而文件面已有 `fs-sandbox` 的 `checkedTarget`（`packages/fs/fs-sandbox/src/index.ts:122-144`）叠加 `approval` 在起作用。所以「工具调用无沙箱隔离」只在恢复终端后才成立。
- **不要**用 `ohos.permission.CUSTOM_SANDBOX`（system_basic / API 18）替代：它改的是应用自身沙箱类型（动态沙箱），不是进程沙箱。

**目录列举 / 内容搜索**

- 根因：`dsh-tool-fs-search` 的 `inject` 是 `['tools','systemPrompt','subprocess']`，靠 `@vscode/ripgrep` **外部二进制**；再叠加 preset 层禁用。
- 已替代：挂 `@deepseek-ai/dsh-tool-str-replace-editor`（**PURE**，`inject: ['tools','fs']`，`src/index.ts:428-435`，其 `view` 对目录路径返回目录清单）；另以纯 JS `grep` 插件（基于 `ctx.fs` 的 `stat`/`listDir`/`readText`，零原生依赖、零子进程）。
- ⚠️ `glob` **只返回文件、从不返回目录**（`glob.ts:314-317`），所以「列目录」不能指望 glob。

**删除 / 移动 / 重命名**

- 现象成立，但**不是鸿蒙限制**：dsh 的 `ctx.fs` seam（`packages/fs/fs/src/index.ts` 的 `abstract class FileSystem`）原语里没有 delete/remove/unlink、rename/move、copy/mkdir/watch；`tool-fs` 只暴露 `read`/`read_image`/`write`/`edit`。包 README 的 Known Limitations 自述只有十余个原语，无 delete / rename / copy / watch。删除 / 移动在 dsh 里**唯一**的原生途径是 shell 的 `rm`/`mv`。桌面版同样没有这些能力。
- 已补齐：`patches/dsh-v0.1.5-rc.2/dsh-fs-remove-primitive.patch` 给 seam 加 **非抽象** `FileSystem.remove`（默认体抛错，避免破坏既有六个 `extends FileSystem` 的子类），`fs-local` 实现放在独立 `remove.ts`，`fs-sandbox` 覆写先走 `checkedTarget`；工具侧由 `plugins/harmony-plugin-fs-mutate/` 提供 `delete` / `move`。
- `patches/dsh-v0.1.5-rc.2/dsh-fs-write-bytes.patch` 之后 `move` 不再受「只能搬文本」限制。

**复制 / 改权限（chmod）**

- `copy` **不需要任何新 seam 原语**：`writeBytes` 补丁已证明「读字节 → 写字节」足以按字节搬运文件（`move` 就是这条路径的拷贝半程 + 一次删除），因此 `copy` 只是在插件层复用同一条路径，并与 `move` **共用同一个规划器**（`lib/transfer.js`），使包含判断、覆盖规则、空目录拒绝三套规则不可能彼此漂移。seam 至今仍无 `copy` 原语，这是**有意为之**：新增原语要付出补丁链与验证成本，换不来任何新语义。
- `chmod` **必须新增原语**：既有变更原语的 `expected`（`FsWriteIntent`）只能表达「缺则建 / 版本则改」，无法表达权限位；而本工程的插件约定禁止直接碰 `node:fs`。故第 13 个补丁 `dsh-fs-chmod-primitive.patch` 按 `remove` 的同一形状补入：**非抽象** `FileSystem.chmod`（默认体抛错，不破坏既有六个子类）+ `fs-local/src/chmod.ts` + `fs-sandbox` 覆写（先走 `checkedTarget`）。
- `chmod` 的实现被 D.2 第 6 条**倒逼**成「应用后回读校验」：`hmdfs` 会接受调用却不落实权限位。若按「调用成功即报成功」实现，工具就会把这种静默忽略**伪装成成功**，比不提供该能力更糟。回读校验把它转成显式 `FS_IO_ERROR`，代价是用户目录上的 `chmod` 必然失败 —— 这是**正确的失败**，且模型能据此判断该换路径而不是重试。
- 附带事实：`copy` / `move` 发布的新文件**不继承**源的权限位（原子写路径为新目标请求 `0600`，且不复制源的模式位），因此「复制后按需 `chmod`」是工作区内的正常用法。

**用户目录写入失败 + 每次审批（两个独立问题）**

| 层 | 内容 | 出处 |
|---|---|---|
| ① DSH 沙箱白名单 | 白名单 = **session workspace 一个根** + `/tmp` + `os.tmpdir()` | `packages/sandbox/sandbox/src/roots.ts:52-55`；`sandbox-policy/src/index.ts:163-170` |
| ② DSH 建文件走硬链接 | `writeFileAtomic` 新建分支走 `link()`，失败无回退 | `packages/fs/fs-local/src/fsio.ts:616-621`；`throwGuardedCreateFailure` 519-554；覆盖走 `rename()` 631-632 |

### C.4 安全：围栏与审批

- **围栏 fail-closed 且生效**：工作区外写入先被 `FS_SANDBOX_DENIED` 拒绝，**拒绝发生在审批之前**（`profiles/desktop/cordis.patch.yml:31` 明确写着 `sandbox-policy`/`pwsh-sandbox`/`fs-sandbox` 不额外禁用）。
- **审批链路完整可用**：UI 会渲染「等待审批」面板（含理由与「拒绝 / 允许一次」两个动作），agent 阻塞等待，拒绝后返回 `the user rejected escalating this operation to "danger-full-access"`。源码侧亦印证 fail-closed：`ApprovalService.decide()` 的 waterfall 终结默认值是 `() => Promise.resolve('unavailable')`（`packages/interaction/user-approval/src/index.ts:274`），调用方对 `unavailable` 一律**拒绝**（`packages/core/tools/src/index.ts:1713-1715`、`packages/sandbox/sandbox/src/escalation.ts:186`）；Web UI 侧由 `packages/client/ui-approval` 的 `ApprovalPanel.tsx` 呈现，注册于 `packages/bundle/web-app/cordis.patch.yml:252-253`。
- 用户目录的可写面由部署期变量 `DSH_EXTRA_WRITABLE_ROOTS` 注入（**不是模型输入**，模型无法自行扩大）；实际生效还需系统授予目录访问并重启应用（见 A.2 #6）。

### C.5 平台可行性：`fork`/`exec` 与 T1 的两个设计约束

实测（PC/2in1、API 24）：`fork` + `execve` + 管道 + PATH 查找**全部放行**；`/system/bin/toybox`、`/system/bin/sh`、`/bin/sh` 均可直接 spawn 并取回正确 stdout；子进程继承应用沙箱（与工作区文件同 uid、无额外特权）。→ **T1 整条路线在平台侧成立；T2（交叉编译 node-pty）确认不必要。**

由此带回两个**必须一并带入 T1 设计**的约束：

1. **子进程退出不可观测 + 僵尸泄漏**。给足 15s，`toybox true`（应立即退出）的事件序列只有 `proc:spawn → stdout:end → stderr:end → stdout:close`，**永无 `proc:exit` / `proc:close`**，同时该子进程在 `/proc/<pid>/stat` 里状态为 **`Z`（僵尸）**。后果三条：拿不到退出码（`cp.exec` **永不回调**）；完成信号只能改用流 EOF；僵尸**每 spawn 一次净 +1、0 被回收**（实测主机侧 30 个僵尸全部挂 Electron 主进程 pid）。→ T1 **必须做成「常驻单 shell 进程」**（一次 `spawn`、stdin/stdout 协议驱动多条命令，僵尸数恒为 1），完成判定用**哨兵行**而非 `exit` 事件，**不要依赖 `exec`/`execFile`**。退出码可用 `sh -c '<cmd>; echo "__RC=$?"'` 打进 stdout。
2. **shell 绕过 fs 围栏与审批**。子进程以同一 uid 运行，却能直接读写用户目录，**不经过 `fs-sandbox` 的 `checkedTarget`、也不弹审批**。→ **这是 T1 落地真正的设计难点**：一旦把 shell 交给模型，C.4 的围栏与审批体系会被整体绕过，子进程只受 OHOS 应用沙箱约束。**必须在 exec 工具层自建路径白名单 / 围栏，或明确接受安全降级；不能只「接个 spawn」就上线。**

### C.6 补丁链上下文约束

`scripts/build-dsh.mjs` 的幂等判据是「`git apply --reverse --check` 成功即视为已应用」，这隐含一条约束：

> **后加入的补丁不得落在既有补丁的上下文窗口内（`git apply` 默认前后各 3 行）。**

**禁区是「连续区间」，不是「固定的 3 行」**：`git apply` 定位 hunk 靠的是「上下文行 + 新增行」构成的那段**连续文本**，并在文件中按偏移重新锚定。因此插入点落在该区间**之外**（之前或之后）就安全 —— 哪怕只隔 1 行；落在区间**内部**（哪怕只是在两条相邻上下文行之间）就会让该 hunk 不再匹配。三条可复用修法：

1. **不要改动被既有补丁整行改过的那一行**（例如 `fs-sandbox` 的单行 import、`fs/src/index.ts` 里的 `FsRemoveOutcome,` 条目），改为**新增一条独立语句**并置于该块之后；若只是往列表里加一项，则选一个**不落在任何 hunk 区间内**的位置 —— `fs/src/index.ts` 的 `FsChmodOutcome,` 就插在两条 hunk 区间之间唯一的空档里。
2. **核对行号时必须先算偏移**：补丁里的 `@@ -a,b +c,d @@` 行号是**该补丁被应用时**的树状态，而**更晚应用的补丁会把其后所有偏移整体推走**。`dsh-fs-remove-primitive.patch` 的 types.ts hunk 写作 `+167`，但在最终树里实际落在 **178–191**，因为更晚应用的 `dsh-fs-write-bytes.patch` 在更靠前处插入了 11 行。把 `FsChmodOutcome` 放在 181 行会正好落进该区间，`remove` 的 reverse-check 立刻失败并精确报出 `types.ts:167` —— **这正是必须靠实测而不是推算定位的原因**。
3. **新补丁一律追加到列表末尾**，这样它的编号与最终树一致；追加前对**每一个**补丁跑一遍 reverse-check。

验证方法：对构建列表里**每一个**补丁跑 `git apply --reverse --check`，全部返回 0 才算通过（当前 **14/14**），再对新补丁做一次「反向 apply → 正向 apply」往返，确认受影响文件的 SHA256 完全还原。

### C.7 图片缩略图：上游没有该功能

用户提问「缩略图在哪里用到」，故做了一次全客户端清点。结论分两层。

**数据源（所有持久化图片共用一条路）**：`ctx.uiConversation.imageUrl()` → `HistoricalImageCache.resolve` → `session.attachment` RPC → host `commands.attachment` → `ctx.attachments.readImage(ref)`。它读的是**已规范化的存储对象**（不是原始文件），且请求类型 `SessionAttachmentRequest` **只有 `{sessionId, attachmentId}`，没有任何尺寸 / 变体参数**（`packages/api/session-controller/src/types.ts:326`）—— 即**没有任何界面请求过小图变体**。规范化目标为 ≤2048×2048 像素预算、编码 ≤4 MiB（`DEFAULT_NORMALIZED_IMAGE_MAX_BYTES`），源文件准入上限 20 MiB；base64 传输再放大 4/3，故单图最坏约 **5.3 MiB 线上字节**。按 session 缓存一次，多个界面共享同一份。

| 界面 | 显示尺寸 | 取数来源 | 单图最坏 |
|---|---|---|---|
| 队列缩略图（durable） | **24×24 px** | `session.attachment` 完整规范化字节 | **≈4 MiB / 线上 5.3 MiB** ← 比值最差 |

| 单张消息图片 | ≤240 px 长边 | 完整规范化字节 | ≈4 MiB |
| 助手正文图片块 | 单张 ≤240 / 多张 64 | 同上 | ≈4 MiB / 图 |
| 工具结果图库（`read_image` 等） | 单 ≤240 / 多 64 | 同上 | ≈4 MiB / 图 |

**可复用但未接线的现成件**：`readImageRequest(ref, policy)`（`attachment-local/src/index.ts:245`）已实现「不放大、按像素预算与字节目标缩放、按变体号缓存、并发合并」，目前**只服务模型请求投影**，未暴露给任何客户端 RPC。真要做缩略图，正确做法是给 `SessionAttachmentRequest` 加一个变体字段并路由到它，而不是另写一套。

### C.8 二进制证书不可得：影响范围与两条替代路线

#### C.8.1 事实与结论

**已确证**：在鸿蒙 PC 上运行**自有 ELF** 必须先取得**二进制证书**（AGC `certType: 4`，受限开放，走**在线工单**）。**个人开发者无法申请**（需企业实体与资质）。因此 **T5（自带 Node / pnpm / python 运行时）对个人开发者不可实现**；T4（`executableBinaryPaths`）虽只差 ACL，但同样以自有 ELF 为前提，**没有企业资质时不必再试**。

> **这不是"某个功能没做完"，而是"一类交付形态被资质闸门封死"。** 它封死的是**载体**（把 ELF 塞进包），不是**能力**（在设备上执行命令、跑 JS、跑 python）。

#### C.8.2 没有证书时：哪些功能无法实现

| 受阻项 | 为什么受阻 |
|---|---|
| **自带 Node 运行时**（011 路径 A） | 需随包分发 `node` ELF → 需证书 |
| **自带 pnpm / npm / corepack** | 同上；且即便有 ELF，`npm i -g` 的 bin 软链在**应用域**被禁（见 C.8.4） |
| **自带 python 运行时** | 同上 |
| **`executableBinaryPaths` 集成 bin**（T4） | 前提就是"自有 ELF"，仍要证书 |
| **市场「一键装插件」的自动供给**（`provisionPnpm()` 自建 pnpm） | 依赖自带上游工具链；无证书时只能退化为"依赖主机已有"或"进程内 JS" |

#### C.8.3 没有证书时：**不受影响**与**可绕道**的功能

| 功能 | 状态 | 绕道方式 |
|---|---|---|
| **命令执行（`bash` 工具）** | ✅ **完全不受影响** —— 已在真机验证 | 它 spawn 的是**系统自带**的 `/system/bin/sh`（mksh R59）与 toybox applet（178 个），**不经手任何自有 ELF，不需要证书、也不需要新权限** |
| 文件类工具（`read`/`write`/`edit`/`delete`/`move`/`copy`/`chmod`） | ✅ | 纯 JS + `ctx.fs` seam |
| 搜索（`grep`/`glob`）、`skill`、子 agent、`workflow`、`web_search`/`fetch` | ✅ | 纯 JS，无原生依赖 |
| 图片（stub + ArkTS 图像桥） | ✅ | 走平台图像框架，不经自有 ELF |
| 市场**浏览 / 搜索 / 更新检查 / 启停** | ✅ | 不依赖子进程 |
| 市场**安装 / 卸载插件** | ⚠️ 可绕道 | **路径 C**：用**主机已装**的 node/pnpm（见 C.8.4）；或 **路径 B**：进程内 JS 跑 pnpm（不需要任何 ELF，见 C.8.5） |
| 在命令里用 `node` / `pnpm` / `python` | ⚠️ 可绕道 | 同上两条；或由用户在系统终端自备（C.8.4） |

#### C.8.4 替代路线一：**依赖主机自带的工具链**（不需要证书）

**这条路线可以解决"pnpm / node / python 从哪来"的问题。** 依据是三项**已实测事实**：

1. **应用的 PATH 里已经包含 `/data/service/hnp/bin`** —— `globalThis.__marketRuntime` 探针读到的 `process.env.PATH` 实测值含该目录（还有 `/data/app/bin`、`/usr/local/bin`、`/bin`、`/usr/bin`、`/system/bin`）。
2. **该目录下已有可用的 node** —— 同一探针的路径 A 诊断实测：`node=/data/service/hnp/bin/node **结构校验通过**`（是合法 aarch64 ELF），**仅缺 `pnpm`**。设备记录另载该目录含 `node npm npx python python3 python3.12`（来自第三方 HNP 包，如 `DevNode-OH` / Python 安装器）。
3. **软链限制只作用于应用域**：实测 shell 域（`id` 显示 `context=u:r:sh:s0`）里 `ln -s` **成功**、`chmod 640` **生效**；被禁的是**应用域**。因此**在系统终端里装的工具可以正常创建自己的 bin 软链**。

→ 因此**只要主机把 `pnpm` 放进某个 PATH 目录**（HNP 的 `install.links` 会由系统建链，或用户在系统终端自行 `npm i -g pnpm`），**应用的 `probePnpm()` 就会成功，市场安装通道即可用** —— 全程不需要二进制证书。

> ⚠️ **第三个"会骗人的探针"**：**`hdc shell` 看不到 `/data/service/hnp`，应用却看得到。**
> 实测：`hdc shell "ls /data/service/hnp"` → `No such file or directory`（**看起来整个 HNP 树都没了**），
> 但**在应用进程内**（`--inspect` → `require('node:fs')`）`/data/service/hnp/bin/node` **存在**：
> `existsSync=true`、`isFile=true`、**size=116,927,320**、`X_OK`，且通过 ELF 结构校验。
> 即 `shell` 域（`u:r:sh:s0`）**被 SELinux 隐藏**了该路径（以 ENOENT 表现），**不代表它不存在**。
> → **凡涉及 `/data/service/hnp`（以及其它 HNP/系统挂载）的结论，必须以「应用域」为观测点**，
> 不能用 `hdc shell` 的 `ls`/`stat` 判断有无。
> （与已有的两个骗人探针并列：`readlink /proc/self/exe` 误报 `/system/bin/toybox`；`uname -a` 的 `Toybox` 是内核字符串。见 FR-4.6。）

**代价与边界（必须如实承认）**：

- **不是产品能力**：用户没装就没有。**不可作为上架功能的承诺**（本工程既有纪律：第三方部署的运行时"属设备环境、不是本应用产物，不得作为产品功能依赖"）。
- **版本/来源不受控**：`process.platform === 'openharmony'`，部分 npm 包会因平台判定失败；第三方 node 由别的应用部署，随时可能被卸载。
- **`npm i -g` 的坑仍在**：若用户是在**应用域**（而非系统终端）里装，bin 软链建不出来（`13900012`）；**必须在系统终端 / hdc shell 里装**。
- **仍需 `node -e` 可用的证据**：设备记录里该第三方 node 的 `node -v` 正常但 `node -e` **无输出**（3 次复现，原因未定位）—— 011 已把 `node -e` 设为路径 C 的**硬门禁**，正是为此。

#### C.8.5 替代路线二：**进程内 JS**（不需要 ELF，也不需要主机装东西）

Electron 主进程**本身就是 Node 22.17**。把 pnpm 与其 dsh CLI 以 **JS** 形式 vendor 进 `dsh-dist/node_modules/`，在主进程内 `import()` 执行而不是 spawn：
**B0（无 node 可执行文件）/ B1（软链被禁）/ B2（用户目录 ELF 不可执行）/ B3（shebang 断链）四个问题同时消失**，且**不需要证书**。
代价：需 patch 第三方 `dsh-market` 的 spawn 点；lifecycle scripts 必须保持禁用；**设备上没有 `git`**（toybox 不提供），故只能装 npm registry 上的包、装不了 `git:` 源。

#### C.8.6 结论

| 问题 | 回答 |
|---|---|
| 没有证书，哪些功能**真的没了**？ | 只有"**随应用自带** node / pnpm / python 运行时"这一件事没了。**命令执行、文件、搜索、技能、子 agent、workflow、图片、市场浏览**全部照旧可用。 |
| 能否绕道？ | 能，且**两条都不需要证书**：**C.8.4 依赖主机自带工具链**（最省事，主机装什么就能用什么）与 **C.8.5 进程内 JS**（最自洽，纯 JS 不落 ELF）。 |
| **"要求主机已有 pnpm"是否可行？** | **可行，且是本场景下最直接的解法** —— 应用 PATH 已含 `/data/service/hnp/bin`，node 已就位且结构校验通过，只差 `pnpm`；主机补上 pnpm 后 `probePnpm()` 即成功，市场安装通道打通。**唯一代价是把它降级为"可选依赖"而非产品能力**，不能写进上架承诺。 |

#### C.8.7 **0.1.5 已决策（2026-09-22）**

> **本版采用路线一：主机装好 `pnpm`；本应用对该能力不作上架（AppGallery）承诺。**

| 项 | 决策 |
|---|---|
| 采用路线 | **C.8.4「依赖主机自带工具链」**（即 011 规格的**路径 C**） |
| 是否上架承诺 | **否** —— 明确降级为**可选依赖**；不得在应用市场描述中承诺"一键装插件" |
| 路径 A（自带 Node） | ⛔ **撤回**（二进制证书对个人开发者不可得，见 D.2 第 17 条） |
| 路径 B（进程内 JS） | ⏸ **暂缓** —— 它是唯一"证书-free 且自包含"的路线；**将来若要让该能力成为可上架承诺，只有它可行** |
| 用户需做的唯一动作 | 在设备**系统终端**装好 `pnpm`（放进应用 PATH 可见的目录，首选 `/data/service/hnp/bin`）。**勿在应用域装** —— 软链禁令只作用于应用域，应用域下 bin 入口建不出来 |
| 验收 | 应用内 `globalThis.__marketRuntime.ok === true` 且 `path === 'C'`；`hdc shell "readlink <目录>/pnpm"` 非空 |
| 仍未验证 | ① 主机补上 `pnpm` 后市场是否真能装插件（需设备复验）；② 第三方 `node` 的 `node -e` 在现设备**无输出**（原因未定位）→ `node -e` 仍作路径 C 的**硬门禁** |

> 与 011 规格的一致性：该决策已写入 `specs/011-runtime-provisioning/spec.md` §4.2，其 Phase 0（证书 / ACL 前置）**整节作废**并新增 `T0.1′`（主机装 pnpm）。

### D.2 平台事实（官方结论与实测事实汇总）

1. **`READ_WRITE_DOWNLOAD_DIRECTORY` / `DOCUMENTS_DIRECTORY` 的 RP 区域标记**：已核对目标 SDK 自身的 `PermissionDefinitions.json`，两项均为 `normal` / `user_grant`、since API 11。
2. **hmdfs `rename` 的文档 / 源码张力**：**实测同目录 ✅ 且跨目录 ✅**（Documents → Download，在同一 hmdfs 挂载内成功）。官方 prose 仍写「仅同目录」，故**现象与解释之间的张力未解**；不据 prose 设置保守契约。
3. **`symlink`**：**实测在工作区与用户目录均返回 `EACCES`** → 官方 prose 成立，现有 `dsh-symlink-to-copy.patch` 的假设继续成立。
4. **`/storage/Users/currentUser` 的挂载类型**：**实测为 `hmdfs`**（`fstype=hmdfs`、`dev=/data/service/el2/100/hmdfs/account`）。此前仅有博客说法，现为实测事实。
5. **`/data/storage/el2/base/files` 的文件系统**：**实测为 `hmfs`**（`dev=/dev/block/platform/b0000000.hi_pcie/by-name/userdata`）。博客的模糊表述「本地 POSIX」被精确文件系统取代。
6. **`chmod` 在 hmdfs 上的语义**：**实测「不报错，但请求的 mode 不被落实」** —— 实际模式由文件系统自行决定。两批证据：① 直接探针连续请求 `600`/`644`/`640`，回读**始终为 `660`**；再请求 `755`，回读变为 `770`。② 经 `chmod` 工具请求 `640` 时，一个原本回读为 `770` 的文件变为 `660`。可见 hmdfs **会**改写模式，但改写值由它自己决定（观测规律：`6xx` → `660`、`7xx` → `770`），**与请求值不对应且不返回任何错误**。对照：工作区（`hmfs`）对 `600`/`644`/`640`/`755` 全部**如实回读**。官方 prose 未覆盖此行为，属已实测事实。→ 这直接决定了 `chmod` 必须做**写入后回读校验**：否则「改了、但不是你要的值」会被当成成功。
7. **Node ↔ ArkTS 通用桥（`systemPreferences.callArkTSFunction` / `callArkTSAsyncFunction`）**：实现在预编译的 `libelectron.so` 内，可从 Electron 主进程按**运行期名字**调用任何经 `JsBindingUtils.bindFunction` 注册的 ArkTS 函数 —— 因此**新增 ArkTS 能力无需改 C/C++、无需重建 `.so`**。实测：返回**标签信封** `{type, value}`；**两个入口都返回 Promise**（「同步」名不副实）；支持 `string`/`number`/`boolean`/`string[]`/`number[]`、参数 ≤3 个、中文往返正确。**两条硬性约束**：① **async 的 ArkTS 方法必须用 `callArkTSAsyncFunction`**，用另一入口调它会**永久阻塞 Electron 主进程**；② **应用被挂起时（如屏幕锁定）调用桥同样会阻塞主进程**，因为 ArkTS 线程不运行。两者都需重启应用恢复。
8. **平台图像能力（运行时列表，非静态常量）**：`image.getImageSourceSupportedFormats()` 返回 12 项 —— `image/bmp`、`image/gif`、`image/heic`、`image/heif-sequence`、`image/jpeg`、`image/png`、`image/svg+xml`、`image/tiff`、`image/wbmp`、`image/webp`、`image/x-adobe-dng`、`image/x-icon`；`image.getImagePackerSupportedFormats()` 返回 5 项 —— `image/gif`、`image/heic`、`image/jpeg`、`image/png`、`image/webp`。**SDK 静态头文件（`image_common.h` 的 MIME 常量）只列了 7 项**，`svg`/`tiff`/`wbmp`/`dng` 仅在运行时可见 —— 查能力必须以运行时列表为准。`ImagePacker.packToData` 直接返回 `ArrayBuffer`（无需临时文件），但其 `PackingOption.bufferSize <= 0` 会静默变成 10 MB，故必须显式设定。

9. **托盘 / 状态栏（2in1）**：`statusBarManager`（`@kit.DeskTopExtensionKit`；旧名 `@kit.StatusBarExtensionKit` 已 `@deprecated since 6.0.0(20)`、`@useinstead kit.DeskTopExtensionKit`）+ `StatusBarViewExtensionAbility`（在 `module.json5` 声明 `type: "statusBarView"`）。syscap `SystemCapability.PCService.StatusBarManager`，**仅 2in1**（其它设备类型调用返回不支持）；绝大多数接口 `@since 5.0.0(12)`，`updateStatusBarHoverTips` 需 `@since 6.0.2(22)`（适配器已按 `deviceInfo.sdkApiVersion >= 22` 守卫），个别接口 `@since 6.1.1(24)`。**无运行时权限要求**。⚠️ 有二手来源称该 Kit 仅限中国区，未能在华为站点直证，属中等置信度，落地前应复核。
10. **「无可见窗口常驻」是官方支持的**：`ProcessMode.ATTACH_TO_STATUS_BAR_ITEM` / `NEW_PROCESS_ATTACH_TO_STATUS_BAR_ITEM` 配合 `StartupVisibility.STARTUP_HIDE`，API 12+、2in1 / 平板，可使 Ability 挂到状态栏图标且窗口隐藏、不占任务栏，再用 `hideAbility()` / `showAbility()` 切换。
11. **无边框窗口（2in1 / 平板自由多窗）**：`window.setWindowDecorVisible(false)`（`@since 11`）隐藏系统标题栏，配套 `setWindowDecorHeight`（11）、`setWindowTitleButtonVisible`、`setWindowTitleMoveEnabled`（14）、`getWindowDecorVisible`（18）。**无需权限**。注意 `setWindowLayoutFullScreen()` 自 API 14 起对 2in1 / 自由窗口不再生效，该场景应改用装饰接口。
12. **更新检查**：`updateManager.checkAppUpdate(context)` / `showUpdateDialog(context)`（`@kit.AppGalleryKit`，`@since 5.0.0(12)`，syscap `AppGalleryService.Distribution.Update`，支持 2in1）。**无需权限**，但前置条件为：已上架、签名一致、安装版本低于商店版本、App 处于前台。**不存在静默自更新的公开 API** —— 它只做「发现新版本 → 跳转 AppGallery」；真正的「自动」由 AGC 分阶段发布 + 用户开启 AppGallery 自动更新决定，App 无法强制。
13. **开机自启无公开 setter**：`autoStartupManager` 仅有只读的 `getAutoStartupStatusForSelf()`（`@since 21`）与 `isAutoStartupSupported()`；唯一设置途径是企业 MDM 的 `applicationManager.addAutoStartApps`（需 `ohos.permission.ENTERPRISE_MANAGE_APPLICATION`，受限 ACL）。第三方应用亦无 `BOOT_COMPLETED` 静态订阅。
14. **通用 ArkTS 桥的接线限制**：桥支持的类型与参数上限（≤3 参、仅 `string`/`number`/`boolean`/`string[]`/`number[]`，D.2 第 7 条）**不足以直接调用运行时既有的 ArkTS adapter binding**。反例：`StatusBarManagerAdapter.SetImage` 有 **8 个参数**，含 `ArrayBuffer` 图标位图与两个函数回调，三项均超出桥的能力。→ **凡是要经桥暴露的既有能力，都应在其前面加一层「JSON 单入单出」的薄包装**（`ImageAdapter.convert` 与本次托盘的 `TrayAdapter` 都是这个形状），而不是试图调用原始 binding。

15. **`executableBinaryPaths` 的权限与 ACL**。官方指南为「应用程序包集成 bin 文件（PC/2in1）」。

    **① 权限名（精确）**：主权限 **`ohos.permission.ALLOW_EXTERNAL_NATIVE_CODE`** —— 官方定义为「允许应用使用外部 native 程序。包括加载外部动态链接库(so)、二进制文件(bin)等」，**system_basic / system_grant / 仅 PC/2in1 / since API 23**，且**在受限开放权限清单内**，即「开放范围为普通应用，但需通过 ACL 跨级别申请」。⚠️ **不存在** `ohos.permission.kernel.ALLOW_EXTERNAL_NATIVE_CODE` 这个名字（`kernel.*` 命名空间检索零命中）—— 按此名申请会直接失败。

    **② 视 bin 行为可能追加的权限**：

    | 权限 | 官方说明 | 级别 | since | 受限 |
    |---|---|---|---|---|
    | `ohos.permission.kernel.LOAD_INDEPENDENT_LIBRARY` | 加载二进制证书签名的共享库 | system_basic | 20（普通应用 22 起） | ✅ |
    | `ohos.permission.INHERIT_PARENT_PERMISSION` | 子进程继承父进程权限（bin 专用） | normal | 23 | ❌ |
    | `ohos.permission.kernel.IGNORE_LIBRARY_VALIDATION` | 独立二进制加载属主 ID 不同的 .so | normal | 20 | ❌ |
    | `ohos.permission.kernel.EXEMPT_ANONYMOUS_EXECUTABLE_MEMORY` | 声明匿名可执行内存（二进制专用） | normal | 23 | ❌ |

    全部为 `system_grant`，**无运行期弹窗**。官方指南另有一句关键限定：「若 bin 文件运行时不需要使用受权限保护的系统能力，则 bin 文件无需声明权限」—— 即**仅仅执行** bin 未必需要 `ALLOW_EXTERNAL_NATIVE_CODE`；官方指南**未逐字点名**该权限，二者语义高度吻合但**逐字关联未证实**。

    **③ `.permission` 是 ELF 节，不是 `module.json5` 字段**（最易误解处）。bin 的权限声明存放在**二进制自身的 `.permission` 节**，内容须为合法 JSON：`{"requestPermissions":[{"name":"<权限名>"}]}`；由 `binary-sign-tool sign … -moduleFile <module.json>` 注入（替代方案 `objcopy --add-section .permission=…`）。**安装期两条硬约束**：bin 声明的权限**不得超过**集成它的 HAP 已声明的权限（否则**整体 HAP 安装失败**）；`.permission` 内容必须是合法 JSON（否则同样安装失败）。

    **④ 构建侧配置**：`module.json5` 的 `module.executableBinaryPaths = [{ path: "libs/arm64-v8a/<bin>" }]`（`path` 必须以 `libs/{abi}/` 开头；标签为 camelCase，指南正文的小写写法是笔误）；配合 `extractNativeLibs: true`、`bundle-profile.json5` 的 `collectAllLibs: true`，且 `deviceTypes` 须含 `2in1`；HAP 侧还须在 `requestPermissions` 声明同样权限。

    **⑤ 「不可用于发布上架应用市场」的精确范围（原文档的混淆点）**：该措辞在官方文档中出现三处，**逐字都指向离线 / 调试手法**：
    - 「直接修改 HarmonyAppProvision 配置文件的方式，**仅用于应用调试阶段使用**，不可用于发布上架应用市场」
    - 「通过 DevEco Studio 完成 ACL 方式跨级别申请权限…**该方法仅用于应用调试阶段使用**」
    - 「本节提供两种调试方法。这两种方式均不可用于发布上架应用市场」

    而同一句话紧接着给出的**正是**正式路径：「如需发布商用版本，请在对应的应用市场**申请发布证书和签名文件**」。→ **被禁的是「本地改文件」那条路，不是 ACL 本身**；ACL 经 AGC 审核后可用于上架。原文档把「不可上架」记为该机制的属性，属**因果混淆**。

    **⑥ 未证实项（不得据以下结论）**：未找到任何官方声明说 `executableBinaryPaths` 机制**本身**被禁止上架 —— 但「未找到」不等于「允许」；真正的闸门是 `ALLOW_EXTERNAL_NATIVE_CODE` 的 ACL 审核（华为对受限权限审核严格，无真实业务场景会被驳回）。另：给 ELF 做代码签名所需的**二进制证书**申请门槛，社区普遍反映较高；官方「申请二进制证书」页为 SPA 未能直取，**未证实**。

16. **HNP（Native 包）事实与打包路径**。⚠️ **本工程已不使用 HNP**（见 A.2 #30）；以下保留为平台事实记录。
    - **形态**：`.hnp` 为归档包，**清单 `hnp.json` 必须位于软件包根目录**，字段 `type`（须为 `hnp-config`）、`name`、`version`（`name`/`version` 不得含空格或特殊字符、目录不得用中文），可选 `install.links[]{source,target}` 声明软链接。归档格式官方正文未明说，但官方实现含 `hnp_zip.c`（ZIP 处理），与社区「.hnp 即 ZIP」一致 —— **文档层面未逐字证实**。
    - **`module.json5` 声明**（**仅 entry 模块**，已核实）：`hnpPackages` 数组，元素含 `package`（**相对 ABI 目录**的路径）、`type`（`public` / `private`）、`independentSign`（可选布尔，API 23+）。HAP 内布局为 `hnp/<abi>/<pkg>.hnp`。
    - **两个工具不可混淆**：**`hnpcli`** 是**打包**工具（构建期，产出 `.hnp`）；**`hnp`** 是**设备端安装**工具（`hnp install -u -p -i -f`，需开发者模式）。社区常见的「hnpcli install」说法是错的。
    - **嵌入 HAP**：`app_packing_tool.jar --hnp-path <hnp 根目录>`（构建期）。`hnpcli` 官方称「已在 OpenHarmony SDK 中提供」，但**具体子目录官方未写**（社区称 `toolchains/`）—— 未证实。DevEco 默认构建是否自动嵌入 HNP，**未证实**。
    - **运行期路径**：public 包应用沙箱路径 `/data/service/hnp/<name>.org/<name>_<version>`，环境变量 `HNP_PUBLIC_HOME=/data/service/hnp`；private 包 `HNP_PRIVATE_HOME=/data/app`。物理路径 `/data/app/el1/bundle/<userId>/hnppublic`（private 为 `.../hnp/<包名>`；userId 默认 100）。**软链接目录 `/data/service/hnp/bin` 默认已加入环境变量**，故用户在系统终端**直接敲命令名即可**调用。
    - **硬约束**：路径长 ≤4096；文件数 ≤65535；单个 hnp ≤4GB。**Linux / macOS / ohos 上打包会继承 UGO 权限，须自行 `chmod 755`**；Windows 上打包则自动赋予 other 可执行位。同名 public 包冲突会导致第二个 HAP 安装失败；卸载 HAP 会连带卸载其 HNP，若有进程占用则卸载失败。
    - **签名**：HAP 必须签名（强制）；包内 ELF 需用 `binary-sign-tool` 做代码签名方能在强制代码签名的设备上运行。
    - **上架**：官方 HNP 指南的表述是「以便后面上传到应用市场」「从应用市场下载 Native 软件包 hap 应用并安装」→ **官方设计意图就是经应用市场分发**，与 T4 的受限权限路线不同。
    - **未证实**：HNP 是否仅限 PC/2in1 —— 官方 HNP 文档**未声明**设备类型限制，但系统终端集成与相关权限均为 PC/2in1，社区一致称仅 2in1，**属未证实的强指向**。

17. **二进制证书对个人开发者不可得**。
    - **机制**：在鸿蒙 PC 上**运行自有 ELF** 必须先做代码签名，签名需华为签发的**二进制证书**（AGC 证书类型 **`certType: 4`**："用于二进制程序签名。二进制程序需使用二进制证书签名，才能在鸿蒙PC上正常运行"）。该证书为**受限开放**，**无自助控制台入口**，只能走**在线工单**申请，工单要求填写**企业名称与资质**。
    - **实测结论**：**个人开发者无法申请**（需企业实体）。因此**任何"随应用分发自有 ELF"的方案在本工程当前主体下不可行** —— 包括 T5（自带 Node/pnpm/python）与 T4（`executableBinaryPaths` 集成 bin，前提同样是自有 ELF）。`-selfSign 1`（本机自签名）**仅可作本地调试**，不可用于发布。
    - **与 HNP 的关系（易混点）**：HNP **机制本身**不需要任何权限/ACL（纯 `hnpPackages` 配置），但**包内的 ELF 仍要过代码签名这道闸门** —— 本工程曾用 HNP 跑通探针（该特性已移除，见 A.2 #30），其载荷是**`#!/system/bin/sh` 脚本**（由已存在的解释器执行，不是 ELF），这正是它当时能跑通的原因。所以 **HNP 不能绕过证书**。
    - **不是同一道闸门**：T4 卡的是 **ACL**（受限权限 `ALLOW_EXTERNAL_NATIVE_CODE`），T5 卡的是 **证书**；**证书这道更严**，没有企业资质时 ACL 也不必申请。
    - **影响范围与替代路线**：见 **§C.8**（结论：受阻的只有"自带运行时"这一交付形态；命令执行 / 文件 / 搜索 / 技能 / 子 agent / workflow / 图片 / 市场浏览全部不受影响；两条**不需要证书**的替代路线为"依赖主机自带工具链"与"进程内 JS"）。
    - **证据**：AGC 证书概述（`certType: 4` 与「需使用二进制证书签名，才能在鸿蒙PC上正常运行」）· AGC 申请证书 API（「二进制证书目前为受限开放，如需体验可通过在线工单系统与我们联系」）· 本工程 `docs/ACL申请清单-v2.md` A1 · 010/011 规格的实机诊断。⚠️ 工单所需企业资质的具体口径以华为工单回复为准，**未逐字取到官方页面**。
